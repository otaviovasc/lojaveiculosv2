# CRM channel connection operations

This runbook covers customer and support operation of Loja Veiculos CRM
messaging connections. Z-API is always visible in the customer Conexao tab as
an optional buyable integration. The customer uses the existing paid add-on
flow; this procedure does not replace Meta business verification or a
provider's account-recovery process.

## Scope and safety

V2 runtime supports the `whatsapp`, `instagram`, and `olx_chat` channels.
Their provider identities are `zapi`, `meta_cloud`, and `olx`; Composio is an
authorization broker for Meta accounts and is never persisted as a channel or
provider identity.
Official WhatsApp and Instagram are included in the R$179/month CRM package;
their onboarding is assisted while the customer completes Meta authorization.
Z-API is an optional Loja-managed service and is configured only after matching
payment evidence. Its price and SKU come from the server-owned catalog and
existing paid add-on flow, never client constants. A connection
belongs to one store scope and its provider is persisted on that connection.
Provider failures do not fall back to another provider because a second attempt
could duplicate a message. A provider-unavailable or indeterminate result must
remain visible as unavailable or failed; it must never be presented as an
official success.

Credential values are write-only and may be entered initially only by an
entitled, authorized customer store owner/admin or a billing-authorized scoped
actor under existing policy. The API and Conexao surface expose only
configuration status and safe reference metadata. Do not paste tokens into
tickets, screenshots, chat, logs, connection metadata, or `credentials_ref`.
The database must contain references or encrypted-at-rest values according to
the deployed credential boundary, never raw provider secrets.

## Required runtime configuration

Configure variables in the API and any CRM schedule worker that composes the
API runtime. Keep local, staging, and production values separate.

- `CRM_CONNECTION_CREDENTIAL_ENCRYPTION_KEY`: stable, high-entropy secret for
  support-managed Z-API connection credentials at rest. Use a different key per
  environment. Do not rotate it by simply replacing the value; use the rotation
  procedure below.
- `CRM_ZAPI_API_BASE_URL`: ZAPI API origin; the committed example uses the
  provider default. A custom origin must be the provider-approved HTTPS base.
- `CRM_ZAPI_CLIENT_TOKEN`: server-owned account-level ZAPI Client-Token used for
  every managed connection. It is never supplied or stored per connection.
  `CRM_ZAPI_TEST_CLIENT_TOKEN` is local-test only; `ZAPI_CLIENT_TOKEN`
  is a deprecated alias and is not read by the CRM runtime.
- Per-connection Z-API webhook secrets are generated by the server, sealed by
  the credential vault, and bound to that connection. The legacy global
  `CRM_ZAPI_WEBHOOK_TOKEN` must not be used for new connections.
- `COMPOSIO_API_KEY`: the only allowed Composio API-key environment reference.
- `COMPOSIO_API_BASE_URL`: optional REST proxy origin; defaults to the Composio
  backend origin documented in `docs/ops/env-vars.md`.
- `COMPOSIO_WHATSAPP_AUTH_CONFIG_ID` and
  `COMPOSIO_INSTAGRAM_AUTH_CONFIG_ID`: distinct server-owned `ac_` auth-config
  IDs used by customer self-service for each official channel. They are not
  connected-account IDs.
- `COMPOSIO_INSTAGRAM_LOGIN_MODE`: exact Instagram auth contract, `facebook`
  for Facebook Login for Business or `instagram` for Instagram Login. The API
  fails closed when it is missing because sender discovery and subscription
  targets differ.
- `COMPOSIO_META_GRAPH_VERSION`: valid `vN.N` Graph version when a connection
  does not carry an explicit non-secret graph version.
- `CRM_META_WEBHOOK_VERIFY_TOKEN` and `CRM_META_APP_SECRET`: Meta GET
  challenge and POST signature verification values for the shared Meta webhook.
- `CRM_OLX_WEBHOOK_ALLOWED_IPS`: optional comma-separated exact-IP allowlist
  for OLX callbacks. Staging and production default to OLX's approved
  `54.162.151.93`; setting the variable replaces that default. Missing request
  source addresses, malformed entries, and unlisted addresses fail closed.
  Set `CRM_OLX_TRUST_PROXY_HEADERS=true` only when Railway is the sole public
  ingress and overwrites `x-real-ip`. Deployed environments reject every OLX
  callback until that contract is explicitly enabled. The API accepts exactly
  one valid `x-real-ip` value and never uses caller-supplied `x-forwarded-for`
  for this authorization decision.

The canonical variable checklist and environment classification are in
[`docs/ops/env-vars.md`](../ops/env-vars.md). Never commit real values to
`.env.example`.

Release check: the authorized customer setup route may accept initial Z-API
credentials only when entitlement, store scope, and actor permission pass;
unauthorized routes must reject them. Credential values are
write-only and responses contain only safe configuration metadata. Confirm the
deployed credential adapter consumes
`CRM_CONNECTION_CREDENTIAL_ENCRYPTION_KEY` before enabling stored-credential
self-service outside a disposable local environment. If the adapter is not
present in the release, use env-reference credentials or stop the rollout;
setting an unused key does not provide encryption.

## Initial setup

### Z-API

1. Find the store's Z-API request by its stable support code. Confirm the
   contract is `paid_awaiting_setup`, belongs to the exact tenant/store, and the
   payment reference matches the scheduled renewal. Never configure a pending
   or merely scheduled request.
2. As the entitled, authorized customer store owner/admin or billing-authorized
   scoped actor, create or select the exact store connection and enter the
   instance credentials. The write-only form accepts them once; existing
   credentials are never returned or logged.
3. Saving valid credentials creates a durable setup intent. Backend/support
   automatically configures all six callbacks: `received`, `delivery`,
   `status`, `connected`, `disconnected`, and `chat-presence`. Callback URLs and
   webhook controls are never shown to the customer.
4. Treat `partial` or `failed` as unavailable. Retry through the same support
   operation using the support code; never create a duplicate connection to
   hide a failed attempt.
5. The customer pairs the provider through the customer-facing QR or phone
   code flow. Continue only when backend setup is complete and the provider
   reports connected.
6. Completion records the connection ID against the paid add-on contract and
   activates `crm_zapi`. The customer-facing support code remains unchanged.
   If the provider is disconnected, the CRM must remain visibly unavailable.

Outside local development, the public API origin must be configured with
`API_BASE_URL` before automatic webhook setup. For local testing, use an HTTPS
public tunnel when ZAPI cannot reach localhost.

When provider-side callback slots drift, platform support may invoke
`POST /api/v1/crm/whatsapp/support/zapi/connections/{connectionId}/webhooks/reset`
with the exact `tenantId` and `storeId`. The operation requires the support
account and paid-entitlement checks, acquires the connection setup lease, and
re-registers all six callbacks against the server-owned `API_BASE_URL`. It is
safe to repeat: Z-API receives idempotent callback-slot updates, while the API
preserves the attempt history and audits reset separately from initial setup.
Treat the returned per-callback results and persisted setup status as the
truth; `partial` or `failed` means the reset did not complete. Returned URLs
are redacted, and operators must not log request credentials or callback URLs.

### Official WhatsApp and Instagram

1. Set the Composio and Meta variables above. Keep the auth-config ID (`ac_`)
   separate from the connected-account ID (`ca_`).
2. Create one short-lived authorization link at a time using the approved
   onboarding surface or the operator diagnostics in
   [`composio-crm-local-test.md`](composio-crm-local-test.md). The connection
   provider selects the channel-specific auth config; never reuse the WhatsApp
   config for Instagram or vice versa.
3. Complete provider authorization in the browser, then verify the connected
   account is active. Never commit or paste the resulting `ca_` ID into a
   public document.
4. Select the explicit WhatsApp number or Instagram professional account. For
   Facebook Login, the Instagram sender and linked Page subscription target
   are distinct and must both match provider discovery. The connection becomes
   ready only after Meta confirms the app subscription.
5. Register `/api/v1/crm/webhooks/meta` as the shared callback URL. It requires
   the configured challenge token and valid `X-Hub-Signature-256` on every
   POST.

Official WhatsApp starts new conversations only with an approved template;
Instagram is customer-initiated. These provider limits are product behavior,
not setup failures.

## Re-authentication

Re-authenticate when the provider reports an expired, revoked, disconnected,
or otherwise invalid account. Do not delete the store connection first: that
can remove the audit trail and makes recovery harder.

For Z-API, an entitled authorized customer actor may replace the instance
credentials through the write-only Conexao form. Support retains recovery,
troubleshooting, rotation/revocation, disconnect, and exceptional setup;
credential replacement automatically starts backend webhook configuration.
Refresh live status and send only a controlled test after setup is complete and
the provider reports connected. For Composio, create a fresh authorization link,
complete consent, verify the new `ca_` account, update the connection reference,
then refresh status. Keep the old provider account disabled or revoked only
after the new account is confirmed.

## Credential and key rotation

Rotate Z-API tokens through the platform-support operation and official-channel
tokens through the provider authorization flow. Record the actual support
actor, paid contract, store scope, connection ID, timestamp, and outcome in the
audit/support system; do not record the secret.

For `CRM_CONNECTION_CREDENTIAL_ENCRYPTION_KEY`, use this sequence:

1. Schedule a maintenance window and confirm a recoverable database backup.
2. Generate a new per-environment key in the approved secret manager.
3. Run the deployed credential re-encryption/migration procedure while the old
   key remains available for reads. Verify every affected connection can still
   report status without exposing credentials.
4. Switch the runtime to the new key, restart the API and CRM worker, and
   perform one scoped status check and one non-destructive webhook check.
5. Retain the old key only for the documented recovery window, then revoke it.

If the deployed release does not provide a re-encryption procedure, stop and
escalate to engineering; replacing the key would make existing credentials
unreadable. The exact command is intentionally not specified here because it
depends on the deployed credential adapter.

## Degraded state, rollback, and diagnostics

Expected degraded states are provider disconnected, missing/invalid runtime
configuration, webhook authentication failure, Composio authorization failure,
provider timeout/5xx, and Redis unavailable. The CRM should show an explicit
unavailable/error state and preserve the request ID or provider event ID for
support. Do not retry ambiguous sends automatically and do not switch provider
to hide the failure.

First-line checks:

- In CRM, refresh live status and confirm the selected store/channel.
- Check the API logs by request ID, `storeId`, `connectionId`, and provider
  event ID. Exclude tokens, message bodies, and raw provider payloads.
- For Z-API, inspect the persisted setup state and confirm all six callback
  types succeeded. Never print the callback URLs because they contain the
  connection-bound secret.
- For Meta, verify the GET challenge and POST signature configuration; there is
  no query-token bypass for Meta events.
- For Composio, run the diagnostic that prints only auth-config/connected-account
  identifiers and status. Confirm the API key is configured under the exact
  `COMPOSIO_API_KEY` variable name.
- If Redis is unavailable, treat in-process fallback as degraded coordination;
  Postgres remains the durable CRM source of truth.

Rollback means restoring the last known-good connection reference/configuration,
not replaying sends. For a bad ZAPI token, restore the prior provider token only
if the provider has not revoked it; otherwise re-authenticate. For a bad
Composio account, point the connection back to the last verified `ca_` account.
For a key-rotation failure, restore the old runtime key only within the approved
recovery window and stop writes until credential readability is verified.

## Product-readiness decision record

- **Target segment:** independent used-vehicle retailers with 15–80 active
  vehicles, one to three locations, and three to 15 operational users.
- **Customer outcome:** a store or agency can buy CRM, request Z-API without an
  immediate prorated charge, contact support at `+55 11 94023-1407`, and see
  honestly whether messaging is scheduled, awaiting setup, or available.
- **Leading metric:** percentage of eligible stores completing a verified
  connection and first inbound/outbound rehearsal within one business day;
  track provider failures separately from successful official operations.
- **Billing treatment:** `crm_core` costs R$179/month and grants `crm`, Official
  WhatsApp, Instagram, and a soft allowance of 10,000 Composio tool executions
  per store/billing month. `crm_zapi` costs R$100/month and grants Z-API only
  after matching renewal payment and support completion. No mid-period
  proration or immediate Z-API provider purchase occurs. The dealership pays
  Meta directly. Archive abandoned sandbox Z-API connections after seven days
  without activity, conversations, messages, or a support hold.
- **Support owner:** CRM/integrations support owner, with engineering escalation
  for encryption, tenant isolation, webhook, or provider-adapter failures.
- **Failure state:** explicit disconnected, configuration-error, or provider-
  unavailable state with no synthetic success and a recoverable diagnostic ID.

The product-event contract is separate from the security audit trail. At
minimum, measure `connection_setup_started`,
`connection_authorized`, `connection_verified`, and `connection_setup_failed`
with store, provider, setup method, elapsed time, and a non-sensitive failure
category. Never attach credentials, message contents, phone numbers, callback
URLs, or provider payloads. Automatic cleanup is owned by the CRM schedule
worker; support uses a hold flag when a paid setup is actively being
investigated.

Commercial enablement still requires the broader gate in
[`docs/strategy/product-operating-model.md`](../strategy/product-operating-model.md).
